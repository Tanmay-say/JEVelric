The Problem

Fraud investigation is too slow, too manual, and too fragmented

Fraud teams at financial institutions are under constant pressure. Analysts must manually gather transaction history, trace money movement, identify connected accounts, review policies, assess risk, document findings, and decide what action to take. This process is slow, fragmented, difficult to scale, and often completes only after the money is already gone.

Each investigation touches transaction databases, device profiles, customer history, closed case archives, regulatory policies, and pattern libraries — all in different systems. By the time a human analyst pieces the picture together, the window for effective action has often closed.

What We Built

An agent that investigates, assesses, acts, and explains

JEVelric is a fraud investigation agent that handles the full lifecycle: from an initial trigger through evidence gathering, uncertainty assessment, policy-compliant action, and a written case record. It processes all 20 HHGOA benchmark cases end to end.

🔍 Trigger → Investigate

Accepts risk scores, customer reports, or analyst requests. Retrieves transaction windows, device profiles, region clusters, email links, and closed case history from TigerGraph.

⚖️ Assess → Decide

Computes fraud probability, identifies patterns (card testing, CNP, account takeover, out-of-region, undocumented), and applies deterministic policy rules R1–R10 to choose actions and approval routes.

🔄 Request → Reassess

When evidence is weak (R1), the agent requests customer validation or step-up auth, simulates the response, then re-evaluates. The recommendation can change — and the agent records exactly what changed and why.

📝 Report → Remember

Files SARs when policy requires it, writes investigation cases to TigerGraph as memory, and validates every ID and field against the live graph before emitting the case file.

Architecture

Orchestration state machine

TigerGraph supplies connected evidence. The assessment layer estimates risk and identifies a likely pattern; the orchestrator uses those signals to settle the case, while deterministic rules R1–R10 select actions and approval routes. The language model writes the explanation and SAR narrative. It does not choose policy actions or routes.

flowchart TD A[Case trigger and intake] --> B[Six TigerGraph evidence queries] B --> C[Assemble graph evidence and local policy context] C --> D{GRAPHRAG_MODE} D -- static --> E[Use static context] D -- grip --> F[GRIP hybrid vector and graph retrieval] E --> G[Assess risk and pattern] F --> G G --> H[Orchestrator settles verdict and case state] H --> I[Apply deterministic policy R1-R10] I --> J{Need more evidence?} J -- "Yes, up to 2 rounds" --> K[Request evidence and simulate response] K --> G J -- No --> L[Finalize actions and approval route] L --> M[Evaluate SAR policy and write narrative] M --> N[Write investigation case to TigerGraph] N --> O[Validate schema, evidence, and graph IDs] O --> P[Emit cases/HHG-xxx.json]

TigerGraph

Three jobs from one graph

TigerGraph is the live evidence store and case memory. Six parameterized GSQL queries retrieve connected transaction, customer, device, region, email, and closed-case evidence. An optional GRIP mode adds hybrid vector and graph retrieval for text knowledge; static mode remains the default.

Base HHGOA: 8 vertex types and 13 edge types. Additive GRIP corpus: 4 vertex types and 2 edge types. Live graph: 590,742 transactions.

🕸️ Graph Database

Customer → Card → Transaction → DeviceProfile relationships power six GSQL queries: card_window, device_neighbors, region_cluster, email_cluster, closed_case_similarity, and customer_history. These retrieve structured evidence with entity IDs preserved — no raw dataframes.

📚 Context Grounding

Static mode assembles local policy and pattern text with graph-derived evidence. Optional GRIP mode searches an ingested corpus of policy, pattern, and closed-case narratives with hybrid vector and graph retrieval. No regulatory reference corpus is currently loaded.

🧠 Case Memory

After each investigation, the agent writes an InvestigationCase vertex with edges to involved cards, transactions, and cited closed cases. Later cases retrieve these as similar_prior_cases — the agent's memory improves with every run.

Agentic Capabilities

What makes this an agent, not just an LLM call

  1. Evidence-round loop — the agent changes its mind When the initial signal is weak (R1: single signal, probability below 0.70), the agent requests customer validation or step-up authentication, simulates the response, then re-evaluates with the new evidence. For example, case HHG-005 started with MONITOR_CONNECTED_CARDS + CREATE_CASE + FILE_REPORT. After step-up auth failed (simulated denied response), the agent added BLOCK_CARD — a materially different recommendation driven by new evidence, not a prompt tweak.
  2. Deterministic policy engine — rules gate every action The policy engine is pure Python, unit-tested, with zero LLM involvement. Rules R1–R10 map signals (fraud_probability, pattern, shared_device_flag, customer_response, exposure_usd) to exact actions and approval routes. The LLM writes summaries and SAR narratives — it never decides what action to take or which route to assign. This makes every recommendation auditable against the published policy.
  3. Approval routing — auto, L1, L2 Only auto-route actions (MONITOR_CARD, VERIFY_WITH_CUSTOMER, CREATE_CASE, etc.) may be executed by the agent. High-impact actions like BLOCK_CARD require L1 (team lead, exposure ≤ $2,500) or L2 (fraud manager, exposure > $2,500) human approval. BLOCK_ALL_CARDS and FILE_REPORT always require L2. The agent recommends and states the route — it never unilaterally blocks.
What We Learned

Real debugging stories from this build

  1. Chunked transport and CSV headers A single large load request was unreliable, so transactions were split into chunks of about 50,000 rows. The upload-capable file-loading path required headerless upload copies and a loading job configured with HEADER="false". Loading job status and live graph counts were checked between chunks until the graph reached exactly 590,742 Transaction vertices.
  2. R1 vs. customer-response policy conflict R1 fires when there's a single weak signal with probability below 0.70 — it recommends VERIFY_WITH_CUSTOMER before any block. But R3 fires when the customer confirms the transaction — CLOSE_NO_FRAUD. If the customer confirmation arrives during the evidence round, R1's VERIFY_WITH_CUSTOMER should be dropped from the final actions, not kept alongside R3's CLOSE_NO_FRAUD. Our unit tests caught this before any case run: the policy engine was union-ing rules without checking for logical conflicts between the "ask" action and the "settlement" action.
  3. Graph-backed ID validation — no made-up IDs The challenge spec states: "Made-up IDs score zero." Our ANSWER_VALIDATE step queries TigerGraph to confirm that every transaction ID, card ID, customer ID, device profile, and closed case ID referenced anywhere in the answer actually exists in the live graph. This caught several LLM-hallucinated IDs during early development — the LLM would invent plausible-looking transaction IDs based on the numeric pattern of real ones.
Current Build & Next Steps

A live graph workflow, with room to extend

  • Live graph investigations. Six GSQL evidence queries ground each case in TigerGraph; the investigation record is written back to the graph and checked against live IDs.
  • Two retrieval modes. Static mode is the default. Optional GRIP mode adds vector and graph hybrid retrieval over policy, pattern, and closed-case text. The public site and live console expose the same workflow.
  • Benchmark delivery. The root cases/ directory contains one answer for each of the 20 HHGOA cases. The static set passed structural and graph-backed validation; public dataset fraud labels were not used to infer outcomes.
  • JEV is future scope. JEV has not been integrated into the active assessment runner. It could later provide an additional typed evidence and uncertainty assessment, evaluated against the current provider path before adoption.
  • Human approval remains a recommendation. L1 and L2 routes are recorded for analyst review; the application does not execute a human approval workflow or automatically carry out high-impact actions.
